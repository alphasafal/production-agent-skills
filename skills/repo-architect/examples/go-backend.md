# Example: Go backend

**Prompt:** "I need to understand this Go service before adding a new gRPC method."

Abridged ARCHITECTURE.md output:

> **System**: Go service exposing both a gRPC API (`internal/grpc/`) and an
> internal HTTP health/metrics endpoint (`cmd/server/main.go` wires both up
> on separate ports).
>
> **Entry point**: `cmd/server/main.go` — loads config
> (`internal/config`), constructs the dependency graph by hand (no DI
> framework), starts the gRPC server and HTTP server, and a background
> goroutine consuming from a NATS subscription (`internal/events/consumer.go`).
>
> **Layering**: `internal/grpc/` (transport, generated + handwritten code
> from `.proto` files in `proto/`) → `internal/service/` (business logic) →
> `internal/store/` (Postgres via `sqlc`-generated queries). `internal/`
> means none of this is importable outside the module — a real, compiler-
> enforced boundary, not just convention.
>
> **Entry points beyond gRPC**: the NATS consumer in
> `internal/events/consumer.go` handles `order.created` events from another
> service and triggers fulfillment logic — a second, easy-to-miss entry
> point into the same business logic used by the gRPC handlers.
>
> **Persistence**: Postgres, queries generated by `sqlc` from SQL files in
> `internal/store/queries/`, migrations via `golang-migrate` in `migrations/`.

Abridged DEPENDENCY_MAP.md excerpt:

> - `internal/grpc` → `internal/service` → `internal/store` (one-directional,
>   verified by reading imports — no back-references found).
> - External: `sqlc` (generated, not a runtime dependency), `nats.go`
>   (event bus client), `grpc-go`.
