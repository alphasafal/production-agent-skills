# Worked example: URL shortener design review

**Prompt:** "Review this design for a URL shortener: single Postgres
instance holds `(short_code, long_url)`, short codes generated by hashing
the long URL and taking the first 7 base62 characters, no caching layer, a
single app server behind a load balancer, redirect endpoint reads from
Postgres on every request."

Abridged SYSTEM_DESIGN_REVIEW.md:

> **Executive summary**: Sound for low-to-moderate traffic; will not survive
> viral-link-scale read traffic without a caching layer, and the hash-based
> code generation has a collision-handling gap.
>
> **Assumptions**: no stated scale target — this review assumes a general-
> purpose consumer product where a small number of links can go viral
> (very read-heavy, highly skewed access pattern), since that's the
> characteristic failure mode for this kind of system.
>
> **Critical risks**:
> 1. Hash-based short codes have no described collision-handling step — two
>    different long URLs can hash to the same first-7-base62 prefix. As
>    written, this is a correctness gap, not just a scaling concern.
> 2. Every redirect hits Postgres directly with no cache — read traffic for
>    a shortener is typically 100-1000x write traffic and highly skewed
>    (a few links get most of the clicks), which is close to a textbook
>    case for a read-through cache.
>
> **Failure scenarios**:
> - If a link goes viral, redirect read load concentrates on one or a few
>   rows; with no cache, this becomes read-heavy load directly on the
>   single Postgres instance with no described read-replica or cache
>   buffer — a likely latency/availability incident under a viral spike.
> - If two long URLs collide on the same short code (risk #1), the second
>   write's behavior is undefined in the design as described — silently
>   overwritten row, or a unique-constraint failure surfacing as a 500 to
>   the user. Needs an explicit decision.
>
> **Recommended changes** (prioritized):
> 1. Add explicit collision handling (check-and-retry with a random suffix,
>    or use a counter/Snowflake-ID-based code instead of a raw hash prefix).
> 2. Add a read-through cache (e.g. Redis) in front of Postgres for the
>    redirect path, given the read-heavy, skewed access pattern.
> 3. Single app server behind a load balancer is a single point of failure
>    for compute — note as a P2 given the assumed early-stage scale, revisit
>    if traffic assumptions change.
>
> **Open questions**: expected read:write ratio and peak QPS target, to
> confirm whether the cache recommendation is load-bearing or precautionary.
